## Contract under test

MoveL, MoveC, and MoveS Cartesian poses represent the controller Active Tool TCP in the configured
Base frame:

```text
MoveL.target_pose = ^B T_TCP_target
MoveC.via_pose = ^B T_TCP_via
MoveC.target_pose = ^B T_TCP_target
MoveS.via_poses[] = ^B T_TCP
MoveS.target_pose = ^B T_TCP_target
```

Only the exact `base_frame` (`base_link` for this HIL) is accepted. The Driver does not default an
empty frame or transform camera, flange, Tool, or other frames. Before a Cartesian Add, it refreshes
and snapshots the controller Active Tool and sends:

```text
coordinate_type = 1
coordinate_id = 0
workpiece_id = -1
tool_id = controller Active Tool ID
```

Actual TCP feedback and stable completion use the same Tool snapshot:

```text
^B T_TCP_actual = ^B T_F_actual × ^F T_Tool_snapshot
```

The default pre-Add guards are 0.05 m translation and 0.1745329252 rad rotation per segment.

## Known limitations

- IO/DO HIL remains deferred.
- HAR/controller source sampling time is not mapped; pose messages use ROS publication time.
- There is no historical flange-pose cache for image-timestamp lookup.
- An external Tool switch requires `get_active_tool` or another lifecycle refresh.
- A controller-side Tool change can still race the Tool refresh-to-SDK-Add interval.
- MoveC and MoveS have software tests only, not physical HIL.
- SDK Euler behavior near singularities has not been physically verified.
- There is no SDK Add mock; pre-Add ordering and pure validation functions provide the software
  evidence for rejected-goal behavior.
- `FollowCartesianPath` is not implemented.
- The request-specific visual three-point utility is not a collision planner.
- The stored visual Base coordinates are fixed results for one request and capture pose.
- Hand-eye absolute accuracy has not completed metrological validation.
